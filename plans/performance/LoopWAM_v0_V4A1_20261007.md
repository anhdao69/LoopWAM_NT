# LoopWAM v0: four video loops, one action loop

This experiment trains from the canonical Wan donor artifact with fresh optimizer state. It follows the late-aligned interface in section 12.2 of the technical report. The video stream executes prelude 3 + core 6×4 + coda 3 = 30 blocks. The action stream executes prelude 3 + core 6×1 + coda 3 = 12 blocks. Its core reads video loop four; prelude and coda read the corresponding video stages. The original v0 executes 4/4 loops (30/30 blocks). Both have 584,536,135 policy parameters. Video computation continues through the first three core repetitions while action state waits; no action computations or gradients are detached.

- Automatic final LIBERO-Long evaluation: 100 episodes (10/task), initial states 0–9, seed 42 with the existing task/episode/replan offsets, 700 policy-step limit, 30 settling steps, ten denoising steps, action chunk 32, execute ten before replanning, CFG 1.0. All episodes save videos on the server.
- Training checkpoint and evaluator record separate video/action loop counts; loading into the wrong architecture is rejected. Only completed ten-epoch checkpoints pass final evaluation.

This is a fresh fixed-depth experiment requested by the user, rather than the optional continuation/mixed-budget objective in section 12.3. Its main control is the original Long-only v0 (96/100 at seed 42), not the full-four-suite v0 checkpoint. Changing microbatch/backend changes RNG assignment, so one training seed is not a statistically conclusive architecture comparison.

## Implementation and validation

The coupled default remains unchanged. CPU checks: 137 passed, two CUDA tests skipped; the GPU allocation checks passed 28 tests. Coverage includes late cache alignment, joint/cached action outputs and gradients, unchanged video outputs, future-frame isolation, checkpointed gradients, strict checkpoint reconstruction and loop metadata, and training/evaluation failure gates. Initial broader tests exposed missing LIBERO import configuration and architecture names omitted from rejection messages; both were corrected and the checks passed.

The original v0 latent cache was rejected because its dataset implementation hash is older. The complete Dense-S30 cache matches the current provenance exactly, including the same source data, split, normalization and native VAE implementation. It contains frozen input encodings, not learned policy state. Production can reuse this cache for speed; training runtime must therefore be labeled as using a precomputed VAE cache. New cold-cache and warm-cache training smoke runs verify the native VAE and gradients before production.
